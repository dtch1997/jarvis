`bellhop` — pip-installable async library that checks code into an ephemeral
RunPod pod (or Modal sandbox), runs it, brings results back, and checks out.
The library successor to **both** legacy compute-runner subagents, which are now
DELETED from jarvis: `runpod-runner` (jarvis PR #92) and `modal-runner` + the
shared `standard-images.json` (jarvis PR #93). Renamed from `runpod-runner`;
bellhop now covers both RunPod and Modal, so nothing falls back to the old
`.claude/agents/*-runner` bash/py drivers anymore.

- **Repo:** dtch1997/bellhop (public; old name redirects); gitignored clone at `repos/bellhop` (`repos/` is wholesale-ignored in jarvis). Package import name `bellhop`, CLI `bellhop run`.
- **On PyPI as `bellhop-py`** (latest v0.5.0, published 2026-07-04, tag v0.5.0; 0.4.0 was never published so PyPI jumps 0.3.0→0.5.0): `pip install bellhop-py` / `'bellhop-py[modal]'` — the bare `bellhop` name is squatted by an unrelated 2022 Django package; import name + CLI stay `bellhop`. Publish flow: `uv build` + `UV_PUBLISH_TOKEN=$(grep '^PYPI_TOKEN=' ~/.env | cut -d= -f2-) uv publish` — the PyPI token is persisted as `PYPI_TOKEN` in `~/.env` (added 2026-07-04 at the user's request).
- **Mechanism:** hits the RunPod **REST API** directly (`rest.runpod.io/v1`) over httpx — NOT runpodctl, NOT the `runpod` SDK; GraphQL only for native TTL. Auth via `RUNPOD_API_KEY` (~/.env). SSH via injecting `env.PUBLIC_KEY` = `~/.ssh/id_ed25519.pub`, then `root@publicIp -p portMappings["22"]`.
- **Two layers:** `async with pod(config) as p:` = composable Pod resource (`exec`/`push`/`pull`/`proxy_url`, multi-step on one pod), with `finally`-teardown on scope exit; `run(spec, cfg)` = one-shot create→ready→upload→run→pull→GCS→teardown + `run_many()` fan-out. Async-only.
- **The crux = "return when functional":** `desiredStatus==RUNNING` lags sshd by 30–60s, so readiness is a pluggable `ReadyProbe` (Ssh/Tcp/Http/LogMarker), default `SshProbe("true")`.
- **GCS upload is opt-in** (default off); pass `gcs_base="gs://..."`. Verified end-to-end on a real RTX 4090 community pod (~42s). Live test: `RUNPOD_LIVE=1 pytest tests/integration_live.py -s`.
- **Safety timers:** native `stopAfter` (24h default) + `terminateAfter` (72h default) via GraphQL `podFindAndDeployOnDemand` (REST has NO TTL field; GPU only — CPU falls back to REST). ⚠️ Set the canonical way (== runpodctl) but RunPod enforces COARSELY — a 4-min timer hadn't fired ~8min late, and runpodctl's own `--terminate-after` behaved identically. Hours-scale backstop, NOT minute-precise; the `async with` `finally` is the primary teardown. Actual firing never directly observed.
- **Modal backend (PR #1, v0.2.0):** second backend behind a backend-agnostic `ExecBox` seam (`backend.py`: `open_box(cfg)` dispatches on type). `ModalConfig` + `sandbox()` (Modal **Sandboxes**, not Functions/`.map`). NB: the once-planned standalone `cloud-runner` Modal-dispatch library ([[cloud-runner-modal-dispatch]]) never materialized as a repo (no dtch1997/ or ArcadiaImpact/ cloud-runner as of 2026-06-30) — bellhop's Modal backend is the surviving Modal substrate. Backend swap = one config line: `run(spec, ModalConfig(gpu="A10G"))` vs `PodConfig(...)`. Modal is SIMPLER: no readiness probe (`create()` returns execable), native TTL as plain create kwargs (`timeout`/`idle_timeout`, no GraphQL), env over API not argv. push/pull = tar-over-**exec** (vs tar-over-ssh). `modal` is an OPTIONAL extra (`pip install bellhop[modal]`), lazy-imported so RunPod-only installs are unaffected. Base error renamed `RunpodError`→`BellhopError` (alias kept). Verified live on a CPU sandbox (~14s, no leaked container): `MODAL_LIVE=1 pytest tests/integration_modal.py`. Modal profile `arcadia-alignment[-team]` in `~/.modal.toml`.

- **Unified backend UI (PR #2, MERGED 2026-07-02):** shared config vocabulary across backends — `gpu=` canonical short names on `PodConfig` too (a `GPU_ALIASES` table expands e.g. `"A100"` to the list of matching RunPod gpuTypeIds; REST takes the whole candidate list → better stock; GraphQL TTL path tries candidates in order), `compute=` derived from `gpu` presence (`None`→CPU, matching Modal), `max_lifetime=` on both configs (→`terminate_after`/`timeout`), `pytorch-cuda` preset pinned to the same torch 2.4.0+CUDA 12.4 on both, CLI single `--gpu` + `--max-lifetime-hours` (`--gpu-id`/`--timeout-hours` deprecated). `gpu_id=` kept as legacy verbatim spelling. `stop_after` vs `idle_timeout` deliberately NOT unified (wall-clock vs inactivity).

- **3600s exec-timeout gap — FIXED in 0.4.0 (issue [#4](https://github.com/dtch1997/bellhop/issues/4) → PR [#5](https://github.com/dtch1997/bellhop/pull/5), 2026-07-03):** `exec()` (protocol + both backends) now defaults to `timeout=None` — no client-side cap; the box's server-side TTL is the backstop (dead SSH still detected via ServerAlive keepalives). Opt-in caps: `RunSpec(timeout=seconds)` on the job step only, `exec(timeout=...)`, CLI `--run-timeout-hours`; expiry raises typed `ExecTimeoutError` (exit code 41) instead of a bare `asyncio.TimeoutError`. Historical gotcha (pre-0.4.0, bit the depth-repro and [[logitban-scale-experiment]] runs): job step silently killed at 1h, results lost.

- **v0.5.0 diagnosis-pass fixes (PR [#6](https://github.com/dtch1997/bellhop/pull/6) MERGED + published to PyPI 2026-07-04, tag v0.5.0):** full-codebase audit → fixes: `max_lifetime` now also CLEARS `stop_after` (default 24h stop was silently killing >24h jobs despite a longer max_lifetime); CPU pods WARN when their requested TTL is dropped (native TTL is GPU-only — silent drop was a leaked-pod risk); Modal `exec(timeout=)` now raises typed `ExecTimeoutError` per the ExecBox contract (was surfacing as plain non-zero exit); `ModalConfig(timeout=None)` warns instead of silently creating a 300s sandbox (Modal has no "unlimited"); `run()` setup+run under `set -e` (failing setup used to continue into run); `run()` salvages partial results+run.log before re-raising a job-step timeout; raising readiness probes = not-ready (retried); COMMUNITY→SECURE fallback reports both errors; GraphQL auth moved to `Authorization: Bearer` header (was `?api_key=` in URL — verified live).

- **v0.6.0 `call()` remote function execution (arsenal PR [#5](https://github.com/dtch1997/arsenal/pull/5) MERGED + published to PyPI 2026-07-14, tag v0.6.0-bellhop; live-verified e2e on a real H100 SXM pod in 34s — test_live_call, GPU overridable via BELLHOP_LIVE_GPU after RTX4090/A40 stock-outs):** the product decision was **"Modal ergonomics on RunPod hardware"** — Daniel considered dropping RunPod for Modal since `call()` copies Modal's interface; conclusion was the opposite (RunPod backend is bellhop's raison d'être — hardware/price/infra; a Modal-only bellhop would be pointless vs using Modal directly). `await p.call(fn, *args, **kwargs)` on both Pod and Sandbox (free function `bellhop.call(box, ...)` works on any ExecBox; protocol unchanged — call() is *derived* from push/exec/pull). Remote exception → re-raised locally as original type with `__cause__` = new `RemoteCallError` (exit 42, `.remote_traceback`). **Python minor-version parity is a hard requirement** (cloudpickle code objects); first call() pre-flights local-vs-remote `%d.%d` and fails fast; cloudpickle auto-installed remotely pinned to local version; check cached per (box, interpreter). `PodConfig.pip=[...]` = deps installed on enter (peer of `ModalConfig.pip`); failure → `ProvisionError` with teardown. Reserved call() kwargs `timeout`/`python`/`echo`/`workdir` (functools.partial escape). Async fns via remote `asyncio.run`. Test gotcha: exec test-doubles must use `bash -c`, not `create_subprocess_shell` (dash lacks `set -o pipefail`). **How to apply:** prefer `p.call(fn, ...)` over `p.exec("python script.py")` for function-shaped payloads returning metrics/configs; large artifacts via GCS/volume paths; match pod image Python minor to the devbox.

- **2026-07-14 field gotchas (sleeper-removal repro, 7 pod attempts):**
  (1) **Always set `PodConfig(name=...)` per experiment and print `p.id` first thing** — every pod defaults to name "bellhop"; with two sessions running bellhop concurrently I deleted my own live run's pod after misattributing it by age. (2) Teardown can SILENTLY fail leaving a zombie (driver printed post-CM "done" but pod stayed RUNNING) — verify with `runpodctl pod list` after a run errors. (3) COMMUNITY A100 hosts can come up RUNNING but never routable (no public port 22) → `PodNotReadyError` at any timeout; use `cloud="SECURE"`. (4) The `runpod/pytorch:*-ubuntu2404` images have PEP-668 externally-managed Python → `pip install --break-system-packages` (or `PodConfig.pip`, which handles it). (5) `p.pull(remote_file, local)` creates `local/<basename>` even for a single file — pull into a dir. (6) For long pod jobs prefer detach-on-pod (`nohup > run.log`) + short poll execs over one giant `exec(timeout=...)` — a timed-out exec gives zero stdout for diagnosis; and don't gate the poll on `pgrep -f <script>` (self-match via the poll's own cmdline — same trap as CLAUDE.md's watcher rule).

**`PodConfig.docker_start_cmd` (arsenal PR #12, MERGED, live-validated):** override the container start command so non-RunPod docker images (which lack the RunPod sshd bootstrap) come up SSH-able and usable as pod images.

**v0.7.0 issue #27 diagnosis (arsenal PR #28, live probe matrix 2026-07-23, `packages/bellhop/scripts/probe_issue27.py`):** the "GraphQL create 500s with custom image + dockerArgs" report was MISDIAGNOSED — the `dockerArgs` single-string spelling is fine (exact failing scimt config creates OK on SECURE). Real story: GraphQL `podFindAndDeployOnDemand` on **COMMUNITY** fails capacity-shaped ("This machine does not have the resources" / transient "Something went wrong") regardless of image/dockerArgs/TTL, and `_gql_create` raised only the LAST ladder attempt's opaque error, hiding that COMMUNITY+SECURE were both tried. Fixes: `_gql_create` now reports every cloud/GPU attempt; `provision_timeout`/`ready_timeout` default to 1200s (from 300/420) when `docker_start_cmd` is set — apt-installed sshd needs 5–15 min. **How to apply:** for GraphQL/TTL pods prefer `cloud="SECURE"` when COMMUNITY errors look capacity-shaped; scimt's `build_flash_wheels.py` comment blaming dockerArgs is stale.
