Bit-for-bit: reimplementing Tinker's training API,
and the gradient bug that proving it caught

JARVIS · 2026-06-17 · draft

We rebuilt the slice of a hosted training SDK our research code actually calls, ran it on our own GPUs, and then tried to prove it behaves identically. The proving is the interesting part — it found a gradient-scaling bug hiding behind a perfectly healthy loss curve.

We run a lot of fine-tuning experiments against Tinker, Thinking Machines' hosted training-and-sampling SDK. Enough that we kept hitting the rate limit — and the rate limit started setting the pace of our research instead of our ideas. So we built our own backend: one that our existing experiment code talks to unchanged, on our own GPUs.

The interesting part of this story isn't that we reimplemented an API. It's what it took to trust the reimplementation — and the real gradient bug that the trust-building process surfaced, a bug that would never have shown up in a loss curve.

Strategy C: clone the call sites, not the API

The obvious move is "reimplement the Tinker SDK." But the full surface is large — RL loops, publish/unpublish, multi-tenancy, billing, audit logs — and we use almost none of it. Cloning all of it is a project with no end.

So we scoped to the slice our code actually calls. Our tinker_cookbook and in-house battery/train/tinker drivers touch a specific set of operations: create a LoRA training client, forward_backward, optim_step, save_state/load_state, save_weights_for_sampler, then sample and compute_logprobs from the trained adapter. That's the surface. We reimplemented exactly that, and made it disappear into the existing import:

import open_tinker
open_tinker.use_as_tinker()   # shadows `import tinker` process-wide

Downstream code doesn't know the difference. tinker_cookbook runs against our backend with no edits.

We also enforced one structural rule that paid off repeatedly: a dependency wall. The client package (open-tinker) depends only on numpy, pydantic, and httpx — no torch, no fastapi. The server (open-tinker-server) depends on the client, never the reverse. This isn't a style preference; it's enforced by packaging. The client installs anywhere in seconds, and the wire contract between the two halves stays explicit instead of leaking through a shared object graph.

The architecture, and the one decision that mattered

The client talks to the backend through an injectable Backend seam. The default HTTPBackend speaks a small JSON-over-HTTP wire protocol we own — tensors go as base64 raw buffers, so float-repr drift never muddies a numerical comparison. A second implementation, LocalBackend, runs the same training and sampling engines in-process, no socket, which makes for fast single-process tests.

battery-sft / battery-distill
        │  (import tinker  ->  open_tinker.use_as_tinker())
        ▼
tinker_cookbook ──Backend──► control plane ──► LoRA trainer (pod, VRAM-resident)
                                            └─► HF / vLLM sampler (in-proc / serverless)
                                                tinker:// blob store on Network Volume

The one decision worth calling out is the hybrid compute split. Training is stateful: the model and optimizer have to stay VRAM-resident across many forward_backward/optim_step calls, so a session is sticky to a persistent GPU pod. Sampling is stateless given a set of weights — so it fans out to separate, scale-to-zero workers. Same wire protocol, two very different compute profiles. The split lets the expensive persistent pod do only the thing that needs persistence, and pushes bursty sampling onto cheap autoscaling capacity. The same protocol runs on RunPod, Modal, and localhost behind one seam.

Proving it: parity, with numbers

"Behaves like Tinker" is a claim, and a claim about a training backend is worthless without numbers. We built a parity harness that runs the identical probe against both backends — ours over an SSH tunnel, Tinker hosted — on the real Qwen3.6-27B.

Teacher-forced logprobs on a fixed 16-token prompt: median absolute difference ≈ 0.011 nats, almost all under 0.03. The single 0.16-nat outlier sits on a near-flat predictive distribution where bf16 rounding moves the chosen-token logprob — exactly the disagreement you expect from the same base model under different inference kernels, not a systematic drift.

forward_backward cross-entropy loss on a fixed batch:

backendloss:sum
ours29.0418
hosted Tinker29.0916

That's a 0.17% relative difference. And a real SFT run on the 27B drove nll from 1.44 → 0.26, with the cookbook fully unaware it wasn't talking to the real thing.

This is the part that makes the rest believable. But it's also where it got interesting.

The bug parity caught

Milestone 1 (SFT + sampling) passed the parity gate cleanly. Milestone 2 added distillation, which introduced a second loss function — importance_sampling, the standard policy-gradient surrogate for on-policy reverse-KL distillation:

$$\mathcal{L} = -\sum_t a_t \cdot \exp\!\big(\log p_\theta(t) - \log p_{\text{sample}}(t)\big)$$

This loss has a knob the cross-entropy path doesn't: the reduction denominator. Do you sum the per-token surrogate, average over tokens, average over masked tokens, or average over sequences? We'd implemented it dividing by total_tokens — the intuitive choice. It looked fine. The loss went down. The code ran.

Then we ran the parity probe. We sent hosted Tinker a one-sequence batch, then the same batch duplicated to two sequences, and watched loss:sum:

batchhosted Tinker loss:sum
1 sequence-6.0593
2 sequences (same datum ×2)-12.1185  ← exactly 2×

Tinker's reported loss exactly doubled. It backprops the summed per-token surrogate, with no token or sequence normalization at all. Our /total_tokens divisor meant our gradient was roughly T× too small — and, worse, the scale factor depended on batch length, so the effective learning rate silently changed with sequence length. A run would still produce a falling curve. It would just be training at the wrong, drifting step size, and we'd have had no way to see it from the metrics.

The fix was one line in the trainer: backprop the pure sum, and demote loss:mean to a logging-only metric. After it, our loss:sum of −6.0441 matched Tinker's −6.0593 to 0.25% — the same agreement band as everything else.

A loss going down is not evidence that your gradient is correct. Reduction conventions, masking, and normalization are invisible in aggregate metrics and catastrophic for reproducing someone else's training dynamics.

The only thing that caught it was differencing against a reference implementation on a controlled input — and the only reason we could do that was that we'd committed to bit-level parity, with raw tensors on the wire, from the start.

A couple of smaller war stories

Two other fixes earned their place in the changelog:

vLLM in a forked subprocess. Running vLLM's V1 engine in-process (or inside a serverless handler) died with "Cannot re-initialize CUDA in forked subprocess." The engine forks an EngineCore; CUDA hates being re-initialized post-fork. Setting VLLM_ENABLE_V1_MULTIPROCESSING=0 keeps it in-process and fixes both the local and serverless paths.

Session eviction. A long-lived control plane with an unbounded session dict OOMs eventually — every training client pins a model + optimizer in VRAM. We bounded it three ways: an LRU capacity cap, a TTL sweep, and an explicit close() that drops the model refs and frees the CUDA allocator pool.

Scale check

LoRA on top of accelerate's naive pipeline sharding got us a validated training step on Qwen3-235B-A22B (an MoE) across 8×H100 — loss 1.85 → 0.58. Naive pipeline keeps one shard active at a time, so it's a correctness-and-stress result, not an MFU-optimal one. Tensor-parallel serving and properly sharded (FSDP/ZeRO) training are the perf follow-ups.

What we did not do

Being honest about the edges is part of the point:

  • Live end-to-end vLLM sampling was never stood up. The box has no Docker daemon to build the sampler image, and we couldn't attach a network volume to a serverless endpoint through the available tooling. The sampler that actually ran — and produced the topk_prompt_logprobs parity numbers (top-1 token match 15/15, top-20 Jaccard 0.956) — is the transformers-based HFSampler, not vLLM. The vLLM fork-fix and handler code are validated and ready for the matched vllm/vllm-openai image; they just haven't run in production.
  • The scope is deliberately narrow. No RL/PPO, no publish/unpublish, no multi-tenancy or billing. It targets the Qwen3.6 family.
  • The async model is v0 — blocking request/response, with futures on the client for pipelining. Submit→poll/SSE is a later revision if long ops need it.
  • No always-on deployment. The validation pod is torn down after each run for cost hygiene.

Takeaway

Reimplementing an API you depend on is mostly unglamorous plumbing — until you try to prove the reimplementation is faithful. That's where the value compounds. The discipline of bit-for-bit parity didn't just give us confidence; it found a gradient-scaling bug hiding behind a perfectly healthy-looking loss curve. If you ever clone a training backend, build the parity harness first. The loss going down will lie to you. The reference won't.
