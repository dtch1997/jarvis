Mailroom Routing

How a captured thought travels from your Todoist Inbox, #lab-notes-daniel, or a voice memo onto a spine — and exactly what mailroom is allowed to do to the original.

source of truth: mailroom/route.py · triage.py runs every 2 h at :15 digest daily 07:33

The pipeline at a glance

Mailroom is two cron commands. mailroom ingest pulls your captures into a local spool — one JSON file per thought, with a per-source cursor so re-runs are idempotent. mailroom route then does two phases over that spool: triage (a model call classifies each new thought) and actuate (a fixed routing table lands it somewhere). The model only ever decides labels; everything that touches your data is deterministic code.

Phase 1 — triage, the classifier

All new thoughts go to a single batched claude -p call (haiku-class, capped per run). The prompt shows the model three registries so it can only pick homes that exist: your curated Todoist projects, your goal file slugs, and the memory/thread slugs from MEMORY.md. It returns, per thought: a type, a one-line title, candidate_slugs, a project or goal when relevant, an arxiv_id if present, and an urgency.

The classification heuristics, verbatim from the prompt:

  • names ongoing work → thread-note
  • a concrete action → todo
  • an idea with no home → research-idea
  • a paper or link to read → paper
  • a statement about direction/strategy for a known goal → goal-signal
  • routine filing → admin
  • genuinely unclassifiable → unclear (stays at the source)
  • when unsure whether something is a task → todo — filing a note as a task costs clutter; closing a task as a note costs lost work

urgency: high is deliberately hard to earn: only if delaying more than ~48 h causes real harm (a deadline, someone blocked, a closing window). Important-but-not-urgent is always low. A malformed model reply never crashes the run — the thought just stays unclear.

Phase 2 — actuate, the routing table

Actuation is a fixed if/elif chain, evaluated in this order. Two things happen per thought: content lands at a destination, and — if the capture came from the Todoist Inbox — the original item gets exactly one of three fates.

the invariant

File, never complete. Completing a task is exclusively your act. The code enforces this structurally — close() is unreachable from the todo/admin branch — and the offline route --check gate fails the run if the ledger ever records a task-completion count other than zero.

Guardrails and edge cases

Idempotent by record
Each thought's spool file carries its triage and route stamps. A routed thought is never re-actuated; re-running the cron does nothing new.
Goal bullets ride a PR
Goal-file edits are deferred to a mailroom/goal-captures branch and only marked routed after the push succeeds — a git failure leaves them pending, and the next run retries. Merge-on-green takes the PR within the hour.
Urgency is batched and freshness-gated
Urgent captures produce one warn-severity flare per run (max 5 titles, then “+N more”), and only for thoughts under 7 days old that aren't backfill — a backlog drain once mass-flared weeks-old captures, so stale can never be urgent.
Cost cap self-reports
Triage batches stop at the per-run call cap; a truncated run sends a warn flare and the leftovers wait 2 hours for the next run.
Slack loop closure
Ingested messages get a ✅ reaction; non-obvious routes (threads note, goal bullet, papers task, flare) also get a short threaded reply saying where the thought went — your receipt at the capture surface.
Policy lives in config
Channels, reply-on-route, batch size, call cap, and the route-threshold gate are all ~/.mailroom/config.toml — a routing correction is a config edit, not code.

known weak spot

Candidate threads seeded from one-off ideas. A note landing on an active project gets seen at the next pickup; a brand-new parked slug (e.g. program-go-teacher-using-katago) has no standing queue pulling it back into view beyond the threads sweep. If anything in this system “vanishes”, it's here.
