JARVIS 2.0 · Design philosophy · 2026-09-08

The Bookkeeper's Bet

JARVIS keeps the books on autonomous research — projects, obligations, spend, and attention — and is deliberately agnostic about what does the thinking.

A working document for Daniel to form an opinion against. It states the position at full strength, then lists the open items where the position is genuinely undecided. Prototype: PR jarvis#189.

ENTRY 01

Provenance: what rotted, what survived

The bet comes from an audit, not an aesthetic. Sixty days of JARVIS 1.0 usage — commits, spool files, importer counts — sort its components cleanly by what they were coupled to.

The 1.0 audit, 2026-09-05
ComponentCoupled toFate

Agent form factors are the fastest-churning layer in the stack: harnesses, models, and multi-agent patterns turn over monthly. Bookkeeping — markdown, git, "every unit of work ends in a recorded outcome" — rots at roughly the rate of the filesystem. A durable system builds on the slow layer and treats agents as replaceable cartridges. The payoff compounds: every time agents get better, JARVIS gets better without changing a line, because it holds state, trust, and attention rather than intelligence.

ENTRY 02

The ledger: projects, ticks, keepers

Three concepts carry the whole system. A project is the unit of long-running work: one directory in git, created from one idea, ended by done, blocked, or dropped. A tick is one unit of autonomous work, bounded by a timeout and a budget. A keeper is whatever advances the project — defined by the contract it honors, not by what it is.

Anatomy of a project — one source of truth per fact
FileHoldsOwner
project.tomlcadence, budget, runnerDaniel
spec.mdidea, motivation, definition of donekeeper drafts, Daniel vetoes
frontier.mdliving working state; a cold keeper resumes from this alonekeeper
state.json · log.jsonlstatus, ticks, costs, outcomes — the audit trailplumbing
reports/checkpoints + final.md — what Daniel readskeeper

Beneath them, one separation does the architectural work: state is the project directory; policy is a prompt contract (keeper.md) edited via PR; plumbing is a single stdlib file that schedules, invokes, verifies, and accounts. Anything that can read and write project files can participate. There is no database, no daemon, and no state outside git.

ENTRY 03

The obligations: strict about behavior

Agnostic about form factor must not mean neutral about behavior. The bookkeeping's entire value is that it is a discipline imposed on whatever agent shows up — and the discipline, not the filing, is the product. Five obligations, all enforced in plumbing rather than hoped for in policy:

  1. Every unit of work ends in a recorded outcome. A tick that ends silent is a broken tick, and the plumbing flags it — the keeper's self-report is verified, never trusted.
  2. Spend is metered at every boundary. Budgets live in config; costs accrue in the log; exhaustion blocks the project and pages Daniel. No open-ended burn.
  3. State lives in files, one source of truth per fact. Views render; they never store. Legible to agents and to Daniel in the same medium.
  4. No silent failures. Timeout, missing outcome, uncommitted work, a stale lease — each is a detected state with a flare attached. Daniel can only forget what he is structurally guaranteed to be reminded of.
  5. Attention is serialized. Four messages out — spec ready, blocked, checkpoint, done — on one channel; two verbs back — edit the file that is wrong, or pause. Draft-and-veto: nothing waits for pre-approval except budgets and unblocking.

These two axes move in opposite directions on purpose: over time the obligations get stricter and more verifiable, while the executor gets ever more swappable.

ENTRY 04

The swap axis: agnostic about form

What a keeper does is policy; what executes it is a runner, chosen per project. The runner's contract is minimal — do the work however you like, return the accounting — and everything protective stays runner-agnostic in the plumbing. Today one runner exists: tick, a bounded headless session. resident (a long-lived session holding a heartbeat lease) and fleet (many communicating subagents behind one accountable lease) are reserved names, built when a real project demands one.

Two commitments made ahead of need. First, "runs for a long time" defaults to many bounded ticks over a durable frontier, not one long process: a crash loses nothing, context lives in files rather than in a session's memory, and the budget re-checks at every boundary. A resident or fleet runner must argue against that baseline. Second, the plumbing never grows orchestration — no fleet logic, no scheduling intelligence, no agent smarts. However many minds a runner fans out to, the books see one accountable keeper per project.

Full agnosticism is a limit you approach, not a place you stand: someone has to ship a runner that works, or the system is a spec nobody runs. The structure is git's — pure plumbing contract, one blessed porcelain — and a contract this clean makes keepers comparable: different form factors on identical projects with identical accounting, so JARVIS doubles as the harness for evaluating its own automation choices.

ENTRY 05

What the books don't buy

Bookkeeping guarantees legibility, not quality. A keeper can record every outcome, respect every budget, and still do mediocre research — 1.0's review bottleneck was never a bookkeeping failure. In this design the quality burden lands in exactly two places: the spec's definition of done, which must be checkable (effect sizes against pre-registered ground truth, not "write a report"), and Daniel's review, which is the attention the whole system exists to protect. That placement is deliberate — taste is the thing worth spending the scarce resource on — but it means the system's leverage on quality runs entirely through spec quality. Spec-drafting is therefore the one agent-smarts investment that pays even under the fully-agnostic framing.

ENTRY 07

Open items

Where the position is genuinely undecided — the part of the ledger Daniel's opinion closes:

  • Lean fully in? Everything above at full strength — JARVIS never grows agent smarts beyond spec-drafting, and all capability arrives via runner swaps. Or reserve the right to build intelligence into the meta-layer later?
  • Auto-activate as the default? Today a drafted spec runs unless paused (veto-shaped, attention-cheap). The alternative — specs wait for explicit approval — buys quality control at the cost of reintroducing Daniel as a blocking dependency.
  • What earns a resident or fleet runner? Name the trigger in advance: which concrete project shape can bounded ticks not serve — true real-time interaction, sub-cadence latency, genuinely parallel exploration?
  • How does attention scale past ~5 concurrent projects? Four messages per project stops serializing at some multiple. Does a desk-like aggregation view return — and if so, as a renderer over log.jsonl, never a second registry?
  • What returns from 1.0 first? Memory consolidation is scheduled; mailroom (thought capture) is validated but not core-loop. The earn-in rule says a real project must need a tool twice — does capture get an exemption as Daniel-facing rather than project-facing?
  • Does spec-drafting get compounding investment? A library of checkable done-criteria patterns, graded retrospectively against how projects actually ended — the one place taste could accumulate in the system rather than in Daniel.
